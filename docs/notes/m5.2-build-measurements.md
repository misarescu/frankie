# M5.2: measuring faster image builds (2026-11-15)

The roadmap's M5.2 item: Goodreads-Clone's toolchain build took 11 minutes in the M5.1 run (unpacking the base image 6 min 13 s, copying a 137-byte `mise.toml` 1 min 46 s, `mise install` 2 min 13 s, exporting 1 min 54 s). This note measures where the time goes and compares the options on the homelab (concrete profile, helm revision 40, runner image `sha-a717546`). Scripts and logs are in `m5.2-build-experiments/`.

## Why builds are slow

BuildKit runs in a Kata VM with its state in an `emptyDir`, which the VM reaches over virtiofs. overlayfs cannot use virtiofs as its upper directory, so BuildKit falls back to its **native snapshotter** (`/var/lib/buildkit/runc-native` in every baseline run), which makes each snapshot a full copy of its parent. The cost is per snapshot, not per byte:

| Step (baseline, `bx-baseline.log`) | Time | What it does |
|---|---|---|
| Extract the 363 MB base layer | 34.5 s | real unpacking |
| Extract a 5 MB layer | 102.9 s | copy of the whole tree so far |
| Extract a 32-byte layer | 102.4 s | copy of the whole tree so far |
| `COPY mise.toml` (137 bytes) | 102.5 s | copy of the whole tree |
| `RUN mise install` | 126.4 s | another copy, then about 25 s of work |
| Export | 109.1 s | diffing the trees |

Downloads are a small share: the base image pulls from GHCR in about 18 s, and the tools in under 10 s.

## Toolchain image (Goodreads-Clone `mise.toml`: go, node, bun, golangci-lint, mockery, sqlc)

Each run is a fresh Job built from `images.BuildResources` (the generator is `generator_test.go.txt`), pushed to `experiments/` in the in-cluster registry. "v2" changes `mise.toml` after "v1", as a toolchain change does.

| Variant | First build | After a `mise.toml` change | Notes |
|---|---|---|---|
| Today: BuildKit, state in an `emptyDir` | **696 s** | (same) | native snapshotter |
| BuildKit, state on a PVC (local-path) | 749 s | 351 s | the base stays unpacked; COPY, RUN and export still copy the tree (still native: local-path is virtiofs in the VM too) |
| BuildKit plus a registry cache (`--export-cache/--import-cache`, mode=max) | 774 s | 752 s | the cache holds layers; the snapshot copies remain |
| BuildKit, state on tmpfs (`emptyDir: {medium: Memory}`) | **99 s** | | overlayfs works; `mise install` 7 s; tmpfs used 3.0 GiB of RAM, pod limit raised to 8 GiB |
| **Append a layer** (no BuildKit) | **83 s**, of which 19 s copy the base image into the registry once per runner tag | **62 s** | install 24-27 s, tar 8-12 s (619 MB), `crane append` 14-15 s |

How append works (`append.py`):

1. An init container runs the **runner base image itself** as the agent user (uid 10001, unprivileged) and runs `mise trust && mise install` with `mise.toml` from a ConfigMap. The node's containerd already unpacked that image with overlayfs, so nothing is copied.
2. A `crane` container tars what the install added (`~/.local/share/mise`, `~/.local/state/mise`, `~/toolchain`), appends it as one layer to the base image's manifest in the in-cluster registry (`crane append`), and sets the `ENV` the toolchain Dockerfile sets (`crane mutate`: `MISE_DATA_DIR`, `MISE_TRUSTED_CONFIG_PATHS`, `PATH` with the shims).
3. The base image is copied from GHCR into the in-cluster registry once per runner tag (`crane copy`, 19 s), so the append only uploads the new layer.

The result was checked in a Kata pod as the agent user: the env matches, all six tools resolve from `~/toolchain/mise.toml` at their pinned versions, the base image's Claude Code is intact, and the mise directory is writable.

## Dependency image (`mise run deps:warm`: `bun install`, `go mod download`, `go build` of 30 packages)

| Variant | Time | Notes |
|---|---|---|
| Today: BuildKit, state in an `emptyDir` | **about 1530 s of build steps**, then the push failed | the registry was OOM-killed (128 MiB limit) receiving the image; a real finding |
| BuildKit on tmpfs | 150 s | tmpfs at 3.9 of 3.9 GiB: one larger dependency set would fail |
| **Append a layer** | **103 s** | warm-up 66 s, tar 14 s (24,935 entries, 672 MB), append 14 s |

Append for dependencies (`appdeps.py`) runs the warm-up in the toolchain image as the agent user, then tars in the same container every path whose ctime is newer than a marker (`find / -xdev -cnewer`; ctime, because unpacked archives keep their files' old mtimes), and appends the tar to the toolchain image. The image was checked: Go modules (405 MB), the Go build cache (145 MB) and Bun's cache (153 MB) are there, owned by the agent, and `go build` of the listed packages compiled nothing, offline.

## Options compared

- **Append** is the fastest for both images (8-11x for the toolchain, about 15x for dependencies), needs the same memory as today (4 GiB), and drops privileged BuildKit (D31): the install runs as the unprivileged agent user and the push needs no privileges, so the build namespace could enforce Pod Security `restricted` like the agents' namespace. It cannot record deletions (no whiteouts), which `mise install` and dependency warm-ups do not need, and it does not run arbitrary Dockerfiles (the Dockerfile escape hatch, D30, is still deferred). The trust model stays D45's: the pod reports a digest, the control plane checks the registry holds it and records it.
- **BuildKit on tmpfs** is close in time and keeps BuildKit, but costs 3-4 GiB of RAM per build on a 16 GiB node, and the dependency build nearly filled it. It is the option to keep in mind for the Dockerfile escape hatch, not the default.
- **A PVC or a registry cache** do not touch the snapshot copies, which are the cost. Rejected. The PVC also forces builds to run one at a time (RWO state).
- **Cheaper compression** (in the roadmap's list): export time is the native snapshotter diffing trees, not compression; append compresses 620 MB in under 15 s. Not needed.

## Also found

- The registry's 128 MiB memory limit is too small: it was OOM-killed receiving the dependency image's push (`frankie-registry` restarted once, `OOMKilled`). Raise it with the build change.
- The `fsGroup` used in the toolchain experiment set the setgid bit on directories; the implementation should not set it.
- Experiment images remain in the registry under `experiments/` and `base/` (the registry's 9.6 GiB of blobs includes them); registry garbage collection is not enabled. The `bx-state` PVC was deleted.

## Recommendation

Build toolchain and dependency images by appending a layer, for both kinds of image, through the same Job and digest path as today (the push container reports the digest as the termination message), with the base image copied into the in-cluster registry once per runner tag. Raise the registry's memory limit. Keep BuildKit only behind the deferred Dockerfile escape hatch.
