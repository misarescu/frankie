# M7.1 gateway chain check (2026-11-19)

D131 (4) has each preview's LiteLLM use the production gateway as its provider, with a virtual key, so no real provider key enters a preview. This check, on Kapsule, tested that before the chart work (open question 22, resolved by D133).

## Setup

All of it was removed afterwards.

- A namespace, `frankie-spike`, with LiteLLM `v1.106.6` (production's image). Its models `claude-haiku-5-5` and `claude-sonnet-5-5` are `anthropic/<model>`, with `api_base` the production gateway's Service and `api_key` a production virtual key: 1 USD, 3 hours, those two models. It has its own master key and no database.
- A temporary NetworkPolicy in `frankie` that let only that LiteLLM reach the production gateway on port 4000.
- A pod from the runner image, `sha-6bb0a0b`, with the runner's Claude Code environment pointing at the chained LiteLLM: `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, and nonessential traffic off.

## The incident

The first attempt put both pods on the platform node (POP2-2C-8G, 20 GB root volume). Pulling the runner image (570 MB) left the node under the kubelet's eviction threshold (10%, 1.8 GiB free). The kubelet evicted the test pods and the production LLM gateway, and tainted the node for disk pressure, so the gateway's replacement waited. The gateway was down from 17:12:47 to 17:19:02 UTC. No issue was running.

After the test pods were deleted, the node had 2.7 to 3.7 GiB free. The largest image there is `kata-deploy:4.3.1` (1.8 GiB), and the Kata install adds to it, although no Kata pod runs on the platform node. Changes that follow from it:
- The check was repeated on the agent pool, whose nodes have 100 GB root volumes.
- Previews never run on the platform node (D131 (2)).
- `misarescu/frankie-cd` limits kata-deploy to the agent pool.
- A platform pool with a larger root volume is the lasting fix. It needs a new pool, since Kapsule cannot resize one.
