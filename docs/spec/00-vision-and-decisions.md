# 00 - Vision and decisions

## Goal

Turn a homelab into a software factory: engineers write specs, role-based agents implement, verify and review them in sandboxes, merges are serialized and automatic once gates pass, and releases move through project-defined stages to production with feature-flag rollout. Strong management UI, workflows, customization and deployment options.

The key distinction: an agent that can write code is not a system that reliably produces software. The value of this project is the control plane, the gates and the delivery pipeline, not the agent loop.

## Non-goals

- Writing our own agent loop or model client.
- Sprints, story points or other human ceremony. Internally a "batch" is a set of ready issues with a DAG.
- Release branches, cherry-picks and back-merges.
- Giving agents any direct cluster or production access.
- Supporting non-Kubernetes execution at first (external executors are a later extension).

## Decision log

Numbered for reference from PRs and issues. Add new decisions at the bottom; never rewrite history, supersede instead.

| D1 | No sprints. Work is a list of issues (specs), optionally grouped as epic > story > task, with a dependency DAG. Engineer sets order or lets independent issues run in parallel, and starts one or many. | Sprints are a human ceremony. |

## Terminology

- **Issue**: a spec. Unit of work for the build lifecycle.
- **Run**: one execution of a workflow for an issue.
- **Step**: one node in a workflow (agent, gate, parallel group, action).
- **Role**: system prompt + skills + tools + MCP servers + model + output contract.
- **Harness**: the agent CLI/SDK (Claude Code, opencode, pi).
- **Gate**: a pass/fail checkpoint of type `command`, `agent-verdict` or `human`.
- **ChangeRequest**: neutral name for PR/MR.
- **Release**: a git SHA plus the set of issues it contains.
- **Stage**: an ordered step in a project's release path (preview, staging, prod, rollout...).
- **Driver**: plugin that knows how to publish, promote, check and roll back for a stage.
| D30 | Toolchain images (M2): the **runner image is the platform base image** (`factory-base`); a toolchain image is `FROM` it plus `mise install` of the repo's `mise.toml`/`mise.lock`, tagged `tc-<hash>` where the hash covers the full base image reference and both files (`internal/images`). Builds run as one-off rootless BuildKit Jobs in the `frankie-build` namespace under the Kata runtime class, with the build context carried in a ConfigMap generated by the control plane (the build pod gets no repo access, token or secret), pushing to a plain `registry:2` whose NodePort lets the node pull as `localhost:30500/...`. Build pods use the egress proxy and its allowlist (D20). The `.factory/Dockerfile` escape hatch is deferred. Supersedes the "version" wording in D15 for the hash input. | A new platform image rebuilds every toolchain image, which keeps the runner in agent pods current at the cost of rebuilds per platform deploy; a separate base version would avoid that but needs the runner delivered another way. Rootless BuildKit needs an unconfined seccomp/AppArmor profile that Pod Security forbids, so the build namespace is `privileged` and the Kata VM is the boundary. |
| D31 | Toolchain builds run **rootful BuildKit as a privileged root container inside the Kata VM**, not rootless. Supersedes the "rootless BuildKit" wording of D15 and D30. | Verified on the homelab: rootless mode fails because `newuidmap` relies on file capabilities, which Kata's virtiofs root filesystem does not honor ("Could not set caps"); rootful BuildKit without privileges fails because `/sys/fs/cgroup` is read-only. Privileged inside the Kata guest works (the pod sees only the guest's devices) and the VM, the no-token/no-secret pod and the egress-restricted namespace remain the boundary. |
| D32 | An agent step runs in the toolchain image of the base branch head **as resolved when the run starts** (`EnsureToolchainImage`, one commit for `mise.toml` and `mise.lock`). A repo without `mise.toml` runs in the platform base image. A toolchain build failure fails the run before any agent pod exists; until M3 adds `onFail` loops there is no retry beyond the Activity's. The workflow change is guarded by `workflow.GetVersion("toolchain-image")`. | The agent should work in the same environment the gates will use; a repo that has not adopted mise keeps working as in M1. A failed build is an environment problem the agent cannot fix, so it is reported instead of started on. |
| D33 | Command gates (M2) run as one pod per gate in the agents namespace, labeled `frankie.dev/role: gate`, in the toolchain image of the commit under test. A `clone` init container checks out exactly the pushed SHA through the git proxy with a **read-only** token (new `ReadOnly` grant; the proxy refuses `git-receive-pack`), and is the only container holding it. Each command (`mise run lint`, then `mise run test`, configurable) runs as its own init container, so the kubelet records each exit code in the pod status; the verdict is taken from those, never from log output, which the checked code controls. A failing command stops the later ones. The result is a `gate_results` row (one per gate StepRun) plus a `gate_result` event with the log tails. Gate pods may reach DNS, the egress proxy and the git proxy only (no LLM gateway). The workflow change is guarded by `workflow.GetVersion("command-gate")`; a failed gate fails the run without a change request until M3 adds `onFail`. | Invariant 2 needs a verdict the agent cannot forge: exit codes recorded by the kubelet qualify, a parsed log does not. Running commands as init containers gets that for free and keeps the pod sequential within the `commandGate` memory budget. The read-only token stops gated code from moving the branch it is judged on. |
| D34 | The platform base image includes **gcc and libc6-dev**, so Go's cgo works in agent and gate pods (`go test -race` needs it). | mise installs language toolchains but no C compiler; without one `-race` fails (`go: -race requires cgo`), which broke Goodreads-Clone's `make test` in the gate and would break the factory's own `test:race` when it self-hosts (M3). About +180 MB per base image, paid once per node and shared by every toolchain image layered on it. |
| D35 | Sidecar services (FR-SB-9) are declared in `.factory/config.yaml` (`internal/config`) and run as **native sidecars** (init containers with `restartPolicy: Always` and a TCP startup probe) of agent and gate pods, reached on `localhost`. The agent pod reads the declaration from the base branch, the gate pod from the commit under test; an invalid declaration fails the run before the agent pod, or fails the gate. A small catalog gives well-known images (`postgres`, `redis`) a port, their own non-root user, a data emptyDir and defaults, so `services: [postgres:17]` works under Pod Security `restricted`. The platform sets the number of services per pod and each one's limits (`controlPlane.services`); those limits are subtracted from the pod's own, which must keep at least 250m CPU and 512 MiB. Services get no egress settings. | Native sidecars order startup (commands wait for the service) and stop with the pod's work without a supervisor. Carving limits out of the pod keeps the concrete profile's memory sheet true whatever a repo declares. The catalog keeps the spec's one-line form usable; repos needing other images declare an object. Verified on the homelab: Postgres 17 as uid 999 in a Kata pod, admitted under `restricted`, ready before the step started (`e2e/services_test.go`). |
| D36 | An agent step **continues the issue's agent branch when it already exists** (an earlier step, or an earlier Run of the same issue, pushed it) and starts from the base branch otherwise. The control plane decides per step (`startPoint`): the runner clones that branch, the toolchain image and services come from its head, and the prompt tells the agent it is building on an earlier attempt. Refines D32, which pinned the agent's toolchain to the base branch head. | Found by the first live M2 run: a re-run started from the base branch and its push was rejected as non-fast-forward by the previous attempt's branch. Continuing keeps git history as the handoff between steps (FR-SB-6), keeps pushes fast-forward without force, lets a re-run fix what a gate rejected instead of redoing the work, and is what M3's `onFail` loops back to `implement` need. Starting over remains possible by deleting the branch. |
| D37 | Sandboxes get Go modules from an **in-cluster Go module proxy (Athens)** on every profile, including the concrete one. Agent, gate and toolchain build pods get `GOPROXY` pointing at it (control plane `sandboxEnv`, which may not set proxy variables) and a NetworkPolicy rule allowing it; Athens accepts only those pods and itself fetches from `proxy.golang.org` with egress limited to public 443. `proxy.golang.org` is removed from the sandbox allowlist and `storage.googleapis.com` is never added; `sum.golang.org` stays, so every module is still verified against the checksum database. Athens runs non-root on a read-only root filesystem with modules on a PVC. Partially supersedes D20's concrete-profile list and docs/spec/09's deferral of dependency proxies for Go. | Found by the live M2 gate: `proxy.golang.org` serves module zips through signed `storage.googleapis.com` URLs, and allowing that host would have opened all of Cloud Storage to agents (the egress proxy sees hostnames only). Athens keeps the sandbox surface to the checksum database while Go builds work. About 0.25 GiB at most. Verified on the homelab: `e2e/go_modules_test.go`, and the first end-to-end M2 run on Goodreads-Clone, whose gate downloaded its modules through Athens. |
| D38 | A sandbox pod's first connections can be refused while the node's NetworkPolicy controller installs the new pod's rules (k3s, measured: refused within 3 ms at container start, accepted 60 to 440 ms later). Code that connects as a pod starts retries: the gate's `clone` container retries `git clone` up to five times with growing backoff (about 10 s in total) before failing the gate; e2e probe pods first wait until the egress proxy accepts a connection and report `net_ready_ms`. Resolves the "first request from a fresh Kata pod" flake noted since M1. | A gate must fail because of the commit, never because its pod started faster than its network rules. Retrying only the connection-bound step keeps the verdict honest: a remote that stays unreachable still fails the gate. |
| D39 | Workflow definitions (M3) are parsed and validated by `internal/config` (`ParseWorkflow`), which **fills in every default** (harness, inputs, gate policy, `onFail: fail`, command gate commands, human gate timeout), so the snapshot in a run's input is explicit. The platform ships built-in definitions embedded from `workflows/` (`default-build`); a project selects one with `workflow:` in `.factory/config.yaml` or adds its own as `.factory/workflows/<name>.yaml`, read from the **base branch head** when a run starts and snapshotted (invariant 4); repo copies are protected paths. Structural rules beyond docs/spec/03: a parallel branch without an `id` is named after its role; `goto` may target an earlier agent step, parallel group or branch of an earlier group (not a gate, not its own group); `maxLoops` is 1 to 10; an `agent-verdict` gate sits only on a parallel group and only after a `command` gate; a `human` gate is always blocking, its rejection fails the run and `onTimeout` is `fail` or `extend`; `budget` is `budgetUSD`. Harnesses and actions not yet implemented (opencode and pi until M4, `merge-queue.enqueue` until M6, `release.create` until M7) are rejected rather than accepted and failed at run time. | Defaults resolved at parse time keep a running workflow independent of a later control plane's defaults. Built-ins give every project a working workflow without copying YAML, while repo definitions keep the repo authoritative (docs/spec/02); reading them from the base branch means an agent cannot change the workflow that judges its own change. Rejecting what cannot run yet turns a run-time failure into a save-time error (FR-WF-5). Escalating a human gate needs a notification channel the platform does not have. |
| D40 | Roles (M3) are parsed by `internal/config` (`ParseRole`, `ResolveRoles`) and the built-ins (`coder`, `code-reviewer`) are embedded from `roles/`; a project may add or replace roles in `.factory/roles/`, read from the base branch like workflows (D39). The **resolved role, prompt text included, is snapshotted with the workflow**. A role ref is `name` or `name@version`; a pin must equal the role file's `version`, since only the current version of a role exists. `output_contract.schema` names a **platform-known contract** (`review-verdict`, `domain.ReviewVerdict`) rather than a schema file, and the platform appends the contract's instructions and JSON Schema to the prompt. `skills` and `mcp_servers` are rejected until the runner can install them; `allowed_tools` is validated now and enforced by the runner with the agent-verdict gate. | Snapshotting the prompt extends invariant 4 to roles: editing a prompt cannot change a run in flight. A repo-defined schema would be one the gate cannot interpret; a fixed contract keeps the verdict parser and the prompt in step (a test checks the schema against the parser). Keeping old role versions around would need a version store; a pin that must match still catches a workflow written against a role that has since changed. |
| D41 | The generic `Interpret` workflow (M3) takes the issue and a **snapshot resolved by the control plane before the workflow starts** (`internal/snapshot`: `.factory/config.yaml`, the definition and roles, all read at one base branch commit), so the definition is in the workflow input itself (invariant 4). An invalid configuration, or one the interpreter cannot run yet, still starts the workflow with the error in the snapshot, so the run fails visibly; a failure to read the repo is retried by the next intake poll. Each step execution is its own StepRun (`attempt` counts executions within the run), agent steps reuse IssueRun's Activities with the step's settings in `StartRunResult.Step`, and a loop back passes the gate's feedback (failed commands and their output tails) to the next agent step that takes the `feedback` input. Rollout: until `Interpret` runs `default-build` (parallel groups and agent-verdict gates), it runs only projects that set `workflow:` in `.factory/config.yaml`; the others keep IssueRun. | Resolving outside the workflow keeps I/O out of workflow code without moving the definition into an Activity result, and reading every file at one commit means a push mid-resolution cannot mix versions. Failing the run instead of not starting it puts a configuration mistake where people look. Reusing the agent Activities keeps one tested path for sandboxing and credentials. Opting in per project lets the interpreter run live before it can run the default workflow. |
| D42 | `Interpret` runs **parallel groups and agent-verdict gates** (M3), and every project now runs on it: a project that selects no workflow gets the built-in `default-build` (ends D41's opt-in rollout; `IssueRun` is no longer started). A group's branches run **one after another** in definition order on every profile for now. A branch whose role has an output contract is a **reviewer**: it reviews the last pushed commit with a read-only git token, a read-only runner workspace (new `Workspace.read_only`: never committed or pushed) and the role's `allowed_tools`, which the runner now enforces (new `StartRequest.allowed_tools`; Claude Code: `--tools`, and `dontAsk` mode with read-only command patterns for `bash:readonly`). The runner also fetches the issue's base branch as `origin/<base>` (`Workspace.compare_ref`) so continuing steps and reviewers can diff against it. `RunVerdictGate` parses each reviewer's final message against the `review-verdict` contract, requires it to cover the commit under review, combines verdicts with `require`, and records one gate result listing every review; a failing gate's feedback is the findings, most severe first. A reviewer without a valid verdict makes the gate **inconclusive**, which fails the run rather than looping back. A `goto` to a branch runs only that branch. | Sequential branches keep the concrete profile within one agent pod at a time and avoid two coding branches pushing the same agent branch concurrently; concurrent reviewers (full profile) need the setting in the snapshot to stay deterministic and come later. Two read-only layers keep a reviewer from changing what it judges: the git proxy refuses its pushes and the runner never publishes its workspace; the tool restriction narrows its behavior on top. An invalid verdict is the reviewer's failure, and sending the coder back on it would spend a loop on nothing. |
| D43 | Human gates (M3, FR-WF-3) wait in `Interpret` for a Temporal signal, `human-gate-decision`, carrying the gate's StepRun ID, approved or not, who and a comment, raced against a timer (`timeout`, then `onTimeout: fail` or `extend`). The pending decision is an **`approvals` row** written only by the workflow's Activities (`OpenHumanGate`, `ExtendHumanGate`, `CloseHumanGate`), which also record a `human` gate result and `state_change` events; the API lists pending approvals (`GET /api/approvals`) and turns a decision into the signal (`POST /api/gates/{id}/decision`, JSON only), and the web UI has an approvals inbox. A rejection fails the run. `onFail: escalate` and a loop that used up `maxLoops` both open an escalation gate (`<gate>-escalation`, 72 h, then fail) where approving accepts the failed gate and continues (FR-WF-4); the latter is a behavior change behind `workflow.GetVersion("escalate-exhausted-loops")`. A definition's human gate opened after `change-request.open` links the change request, so the diff is read on the provider. | A signal keeps the wait inside Temporal with no polling, and a stale or repeated decision is harmless because it names the gate and the first decision stands. Keeping the workflow as the single writer of approvals avoids the API and the workflow disagreeing about a decision. Without authentication (open question 7) the decider is self-reported; the API stays behind port-forward or Tailscale until that is settled. |
| D44 | Protected-path and test-removal detection (M3, invariant 6) runs in the control plane on the **provider's diff** of the run (GitHub compare from the snapshot's base commit to the last push, paginated, `internal/guard`), once the definition's steps have passed. Its patterns are the platform's defaults (`.factory/**`, toolchain, CI and lint configuration) plus the repo's `.factory/protected-paths.yaml`, which can only add; both are read from the base branch into the snapshot, so a change cannot loosen the rules it is judged by (the file is itself protected). A protected path changed or renamed away, a deleted test file, an added skip marker, fewer test declarations, an uninspectable test diff or a diff too large to list forces a `protected-changes` human gate after the change request opened (D43; 72 h, then fail). Behind `workflow.GetVersion("protected-changes")`. | The diff from the provider is outside the agent's reach, unlike anything computed in its pod. Checking the final commit once, at the end, covers every loop's changes and puts the gate where the person can read the whole change request. Heuristics err towards a spurious gate rather than a missed skip, and an incomplete diff is treated as a finding. A rename away from a protected path counts, otherwise moving a file would launder it. |
| D45 | Resolves open question 15. **Toolchain images are run by digest, and only digests the control plane recorded count.** Builds push by digest only (BuildKit `push-by-digest=true`, no tag) and write their result with `buildctl --metadata-file /dev/termination-log`; the control plane reads `containerimage.digest` from the build container's termination message in the pod status, checks the registry holds the manifest under that digest, stores it in Postgres (`toolchain_images`: repository, tag, digest) and then tags the image for people (best effort, never read back). `Ensure` looks up the recorded digest, checks the registry still has it (rebuilds if the registry lost it) and returns `host/repository@sha256:...`; a tag in the registry without a record is ignored and the image is built. Images built before this have no record and are rebuilt once. | The registry stays unauthenticated on the concrete profile, and a build pod that runs unreviewed `mise.toml` content could overwrite any tag. Pinning by digest needs no registry auth or new service: a manifest's address is its content, and the record of which digest belongs to which inputs lives where build pods cannot write. The termination message is written by `buildctl` in the build container, outside the BuildKit sandbox the untrusted RUN steps execute in. A poisoned build can still only poison its own inputs' image, which its own `mise.toml` controls anyway. |

| D47 | **Dependency images** (M3.1). A repo declares `dependencies: {files: [globs], run: <command>}` in `.factory/config.yaml`; the control plane resolves the globs against the commit's file tree, reads the files (at most 200, 512 KiB), always adds `mise.toml` and `mise.lock` (mise resolves the warm-up's tools from them) and builds an image `FROM` the recorded toolchain image by digest that copies them to `/workspace/deps` and runs the command there as the agent user with the sandbox environment. Its tag hashes the toolchain image's repository and digest, the command and every file's path and content; it lives in `dependencies/<repo>`, is recorded and run by digest like toolchain images (D45), and agent steps and gates run it when declared. The command is a JSON exec-form `RUN`, never Dockerfile text.
