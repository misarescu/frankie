# 10 - Roadmap

Ordered to get a working end-to-end slice early, then layer the product. Steps 2 and 3 alone reproduce most of a typical work setup (sandboxed, tracker-agnostic); everything after is the product. Each milestone lists acceptance criteria that can be turned into issues and e2e tests. Milestones are specs for the factory itself and, after M3, are candidates to be run by the factory (see `08-self-hosting.md`).

Every milestone must run on the **concrete profile** (see `09-deployment-profiles.md`).

## M0 - Explore and scaffold (no product code)

- Run Vibe Kanban and Gas City against a toy repo; record what to keep and what annoys you in `docs/notes/exploration.md`.
- Repo skeleton per `01-architecture.md`: Go module, `mise.toml` with tasks `build test lint generate e2e`, buf config, sqlc config, migration tool choice recorded in `docs/spec/00`, CI running `mise run lint test`.
- Helm chart skeleton and Flux manifests for a k3s dev cluster.
- **Done when:** `mise run build lint test` is green on an empty-but-structured repo in CI, and the exploration notes exist.

## M1 - One issue, end to end

Go service takes a GitHub issue and produces a PR from a Claude Code run in a sandboxed pod.

- Control plane with Postgres store (Issue, Run, StepRun, Event), minimal API.
- Temporal (single binary) with a hardcoded minimal workflow: launch agent pod, wait, open ChangeRequest.
- Runner (gRPC `Start/Prompt/Abort/Events`) wrapping Claude Code stream-JSON.
- Pod sandbox: Kata runtime class, NetworkPolicy plus egress proxy (D20), git proxy with a per-step token limited to `agent/<issue-key>/*` (D21), no service-account token.
- LiteLLM gateway with per-run virtual key and budget (real keys never in the pod).
- `GitProvider` + `IssueSource` for GitHub.
- Live log streaming to a minimal UI page (Postgres LISTEN/NOTIFY).
- **Done when:** labeling a GitHub issue `factory` on a toy repo results in a PR on `agent/<issue-key>/*`, with the transcript streaming live and replayable afterwards, within the concrete profile's memory budget, and an attempt to push to `main` or reach a non-allowlisted host from the pod fails (tested).

## M2 - Toolchains and deterministic gates

- Platform base image `factory-base:v1`; per-repo `mise.toml`; image hash/build/push to `registry:2` via one-off BuildKit Job.
- `command` gate: fresh pod from the pushed commit running `mise run lint` / `mise run test`.
- Sidecar services declared in `.factory/config.yaml`.
- **Done when:** a gate fails on a commit whose agent claimed success but whose tests fail, and the image for an unchanged `mise.toml` is reused rather than rebuilt (tested).

## M3.1 - Dependency images (build reuse)

Agent steps and gates start every pod with empty dependency and build caches, so a repo's dependencies are downloaded and compiled on every run: Frankie's first gate (frk-1) took 17 minutes, most of it fetching Go modules and compiling dependencies, twice (once for `lint`, once for `test`). M3.1 bakes a repo's dependencies into an image layer, in a way that works for any ecosystem, not only Go.

- `dependencies` in `.factory/config.yaml`: the files the warm-up reads (globs relative to the repo root, e.g. `go.mod`, `go.sum`, `**/pom.xml`, `build.gradle.kts`, `uv.lock`, `requirements*.txt`, `**/*.csproj`, `packages.lock.json`, `conanfile.txt`, `web/bun.lock`) and a `run` command, normally a mise task, that downloads them and pre-compiles them where the ecosystem allows. The platform has no per-language logic; the repo decides what to warm (docs/spec/05).
- **Dependency image**: `FROM` the repo's toolchain image by digest, with the declared files at their repo paths and the warm-up run as the agent user with the sandbox environment, so every ecosystem's cache lands where it looks at run time. Tagged by a hash of the toolchain digest and the files; built, verified and recorded by digest like toolchain images (D45). Agent steps and gates run it in place of the toolchain image. Repos without `dependencies` keep today's behavior.
- Changed dependency files rebuild only this layer (minutes), not the toolchain (about 13 minutes for Frankie); unchanged files reuse it.
- Caches live only in image layers built from the declared files; whatever an agent or gate pod writes stays in that pod, so no run can poison another's cache (invariant 2).
- Hosts a warm-up needs (Maven Central, NuGet, ...) go through the egress allowlist as usual.
- **Done when:** Frankie's gate with unchanged dependencies takes at most 6 minutes on the concrete profile (17 at M3); unchanged dependency files reuse the dependency image and a changed `go.sum` rebuilds only the dependency layer (tested); a non-Go toy project (Python or Java) gets a working dependency image from its own declaration (e2e).
- **Done (2026-11-13):** Frankie's frk-2 ran in its dependency image: gate 4m46s (frk-1: 17m18s), agent step 5m38s (14m12s) (frankie#44). Activity tests cover reuse and the `go.sum`-only rebuild; the `dependencies` e2e builds and runs a Python toy's dependency image. Building a dependency image is slow (Frankie's: 29m44s), almost all of it BuildKit unpacking and copying the toolchain image inside the Kata VM (open question 16 d).

## M5.2 - Sandbox and builds

Fixes found by the M5.1 acceptance run, before the merge queue: projects configure their sandbox, builds get faster and visible when they fail, and pods are sized from measurements.

- Per-project egress: a project adds hosts to the platform's allow-list in `.factory/config.yaml` (`egress.allow`), read from the base branch at start (invariant 4) and protected (invariant 6). Plain hostnames only, validated; the deployment can refuse project additions (`egressProxy.projectAllow`). The egress proxy learns each pod's project from a short-lived signed token, like the git proxy, and checks the destination against that project's list. The Helm list stays the baseline.
- Shared builds: runs waiting for the same image build see its outcome; one run's failed attempt no longer leaves another with "job not found".
- Failed build logs are kept (a failed build's last lines reach the run's transcript), so a broken build says why.
- Faster builds: measured on Goodreads-Clone's toolchain build (11 min: unpacking the base image 6 min 13 s, copying a 137-byte `mise.toml` 1 min 46 s, `mise install` 2 min 13 s of which downloads 28 s, exporting 1 min 54 s). Try, measure and pick: BuildKit state on a block volume or a registry cache, appending a tools layer to the base image's manifest instead of rebuilding it, cheaper compression. Measured (`docs/notes/m5.2-build-measurements.md`): BuildKit falls back to its native snapshotter on the Kata VM's virtiofs, which copies the whole tree for every snapshot; appending a layer built in the base image itself took 62-83 s for the toolchain (from 696 s) and 103 s for the dependency image (from about 25 min), BuildKit on tmpfs 99 s and 150 s at 3-4 GiB of RAM, a PVC or a registry cache barely helped. The registry (128 MiB) was OOM-killed receiving a dependency image. Implemented by appending a layer for both kinds of image (D81): no BuildKit and no privileged build pods, the base image mirrored into the in-cluster registry once, the registry given 512 MiB.
- Pod sizing from the M5.1 samples (5 s samples over both epics, `kubectl top`): agent pods used a median 0.86 CPU (p90 1.81, max 1.86) and 1.0 GiB (max 2.6 GiB); gate pods are CPU-bound (median 1.81 CPU, memory under 1 GiB); build pods are I/O-bound (median 0.15 CPU) with memory up to 2.87 GiB against their 3 GiB limit. The node never used more than 2.5 of its 4 CPUs or 6 GiB of 15 GiB, yet 12 pods waited `Pending` for a minute or more (42 minutes in all, up to 8 min for a gate) because every pod requested 2 CPUs. Separate CPU requests from limits (e.g. agents 500m, reviewers 250m, gates 1 CPU, builds 250m, limits unchanged), keep memory requests equal to limits, and raise the build memory limit.
- A refinement or run that fails before its agent starts (image build, pod) does not hold the draft (D66 holds it only for a bad refiner result), and an issue page offers "Refine again" on a held draft, also when a parent's request covers it.
- **Done when:** a Goodreads-Clone epic with independent tasks runs with two slots without a pod waiting on CPU requests, a toolchain change rebuilds in a fraction of today's 11 minutes, a project adds an egress host in its own config, and a failed build shows its error on the issue.
- **Done (2026-11-15):** Goodreads-Clone's "Reader profile" epic (gc-35, #69: three independent tasks) ran with two slots: two tasks started together and the third took the first freed slot, and no pod waited to be scheduled (no `FailedScheduling` event; three pods at once requested 1.75 of 4 CPUs, the node peaked at 3.63 CPUs and 8.0 GiB). Goodreads-Clone's toolchain image rebuilt in 60 s and its dependency image in 95 s by appending a layer (D81), with `nodejs.org` coming only from the project's own `egress.allow` (D80); the first attempt without that host failed in 39 s with the build's log on the run (D79). Acceptance found and fixed a retry that failed for finding its work done (D82) and a Claude Code session held open by a background task (D83). Findings left open: registry garbage collection (open question 17, planned for M6) and the egress bootstrap (open question 18), and coders peaking at 2.59 of 3 GiB. Notes: `docs/notes/m5.2-acceptance.md`.

## M6 - Merge queue

- Per-repo queue workflow, signal-with-start enqueue, rebase/conflict/red handling (`06-delivery.md`).
- Auto-merge once gates pass, and once the change request's provider checks are green too (`GitProvider.CommitStatus`): in the M5.1 run a repo's own CI failed where Frankie's gate passed.
- Conflicts go back to the coder with both sides: in the M5.1 run they were in registry-style files (repository interfaces, struct fields, mock config, imports in `App.jsx`) where keeping both is right.
- Approve and reject a change request from Frankie: approving merges it (through the queue), rejecting closes it and sends the issue back with the reason (resolves open question 11). An issue moves to `awaiting_human` while a gate or question inside its run waits, without the merge watcher recording a merge under a running workflow (D76).
- Visibility: a step waiting for an image says it is building the toolchain or dependency image, and the issue page streams the build's log; a gate that passed while the provider's CI failed on the same commit is shown on the issue.
- Bug-fix workflow, built in next to `default-build` and selected by issue type (`workflows: {bug: bug-fix}`): a read-only `investigate` step with a findings contract (root cause, evidence, how to reproduce, whether a test can), a human gate only when no test can reproduce it (approve, send back with feedback, or cancel), a `reproduce` step that pushes only a failing test, a command gate that must fail, `fix` without touching that test, checks, a review that checks root cause and the test, and a change request naming the root cause. Needs conditional gates, `expect: fail` command gates and per-type workflow selection. Implemented (D94-D96): per-type selection with `bug` -> `bug-fix` built in, a `bug-findings` contract, `when` conditions, `expect: fail`, a `preserve` gate and human gates that send back.
- Registry garbage collection (open question 17): the in-cluster registry never deletes anything, and every runner tag adds a mirrored base image and each project's rebuilt images (10.4 GiB on a 10 Gi volume after M5.2). Delete the manifests no `toolchain_images` record points to and the mirrored bases of runner tags no longer deployed, then run the registry's garbage collection on a schedule. Implemented (D84): daily, when no build runs, keeping the three newest images per repository and any built within a day, with garbage collection in the registry's init container on a restart.
- **Done when:** two issues editing overlapping code both reach `main` with the second being sent back to the coder on conflict and re-reviewed; `main` is never red; a change request is approved and merged from Frankie; a Goodreads-Clone bug runs the bug-fix workflow from investigation to a merged fix with its reproducing test.

Registry collection took the registry from 7.3 to 4.4 GiB. The run led to D97 (a `preserve` gate keeps the lines a step added) and D98 (skipped steps shown as such). ## M9 - UI overhaul

The UI grew page by page since M1: hash routes, one stylesheet, each page polling on its own, and pages that do not lead into each other. M9 rebuilds it on a component library with one shell, real URLs and a shared cache, ports every page, and shows what a story or an epic cost in all. The API changes only for that cost (D142). The look and the flow were agreed on a clickable mockup (`docs/notes/m9-ui-mockup/`); it lands as one change request.

- **Stack (D141):** shadcn/ui components owned in `web/src/components/ui/`, Tailwind CSS v4 through Bun's bundler, TanStack Router with path URLs, TanStack Query for server state, a Cmd-K search palette, light and dark themes. The web deployment stays one Bun pod on the concrete profile.
- **Shell:** a sidebar with the project switcher (`GET /api/projects`; the last project is remembered), Board, Runs, Approvals with the number of things waiting for a person, and Releases; a header with breadcrumbs (project > epic > story > task > run > step), search over issue keys and titles, runs and pages, and the theme. The name (M5.1) and the API token (D58) move into a menu in the sidebar's footer. At phone width the sidebar becomes a drawer.
- **URLs (D141):** `/projects/{project}/board`, `/projects/{project}/runs`, `/projects/{project}/releases`, `/issues/{key}`, `/runs/{id}`, `/releases/{id}`, `/approvals`, with tabs, views, filters and the selected step as search parameters. Every navigation is a history entry, so back and forward walk pages, tabs and steps, and a reload or a shared link opens the same view. The M5-M7 hash URLs redirect.
- **Board:** a summary (running, waiting for a person, merged, spent); the hierarchy as a collapsible tree with status, a parent's progress over its leaves, what each issue waits for, cost (a parent shows its total, with its own cost beneath), change request and latest run; finished issues on request; start selected, with the scheduler's reply (starting, waiting and why, overlaps); a dependency graph view.
- **Issue page:** key, type, source link, status and the actions that do something (D72); a banner for what waits for a person on this issue (a human gate, an agent's question, a refined spec), decided in place; a summary (cost, or total cost for a parent; change request or progress; runs; what it waits for); tabs Overview (the live run card, spec, acceptance criteria, issues under it, relations, overlaps, changed paths, details), Runs, Issues (a parent's subtree with each issue's total and a total row, D74) and Activity (sync, start requests, spec decisions, runs and closing, from the issue's own fields).
- **Run page:** the steps on the left, with status, role and model or gate type, duration, cost, loop-backs, skipped steps with their condition (D98) and steps not reached yet (D73); the selected step's transcript on the right, labeled as in D67, tool calls folded except shell output, a gate's result per command or reviewer; steer and abort at the bottom for a running agent step (D52).
- **Runs page:** the project's runs, newest first, filtered by all, active or failed; release runs named by their release.
- **Approvals:** one inbox across projects, filtered by kind: human gates (protected changes, merge approval, bug-fix decisions, release stages, D139), agents' questions and refined specs, each decided in place, with links to its issue, run and change request.
- **Releases:** the list with each release's stages, and a release's page with its stages, verifications and failed tests, notes, issues, bug issue and the release agent's runs, and the production gate in place.
- **Cost (D142):** an issue's total includes everything under it, so a story shows the sum of its tasks and bugs and an epic the sum of its stories, on the board and on its page.
- Not in M9: sign-in and settings (M10, M11), editing a spec in the page, a merge queue view.
- **Done when:** every action of the M8 UI works from the new one (start, retry, complete, cancel, gate decisions with request changes, answers, approving and rejecting refined specs, steer, abort, release gates); every page, tab and selected step has a URL that survives a reload and the back and forward buttons; an epic and a story show the cost of everything under them on the board and on their page; a Goodreads-Clone issue is watched live from the board to its merge on Kapsule; it works at phone width and in both themes; the web pod stays within its concrete-profile budget.

## M10 - Sign-in and public access

Frankie's UI is reachable only through port-forward, because anyone who reaches the API can read every transcript and, with the token, decide any gate (open question 7). M10 adds people: users who sign in, roles that limit what they do, and a public address for the UI. The design is confirmed as decisions when the milestone starts; the plan:

- **Users and sessions in Postgres** (invariant 8): users, the identities linked to them, and sessions, carried in an HttpOnly, Secure, SameSite=Lax cookie; writes also check `Origin`. Built into the control plane, so the concrete profile gains no service (Dex was the alternative).
- **Sign-in:** username and password first (argon2id, rate-limited), then single sign-on with Google and GitLab (OIDC) and GitHub (OAuth); a person can link several.
- **Who may sign in:** the first administrator from a bootstrap secret; then people invited by an administrator, or matching an allowlist (an email domain, a GitHub organization).
- **Roles:** administrator (users; connections and repositories from M11), member (start, retry, complete, cancel, decide, answer, steer, abort), viewer (reads only).
- **Every request is authenticated**, reads and the event stream included; decisions, answers and start requests record the signed-in person instead of the name the browser sends, which closes open question 7. Scripts use per-person API tokens in place of the single token (D58).
- **Public access:** only the web deployment is published, at a hostname on the user's Cloudflare domain, through a Cloudflare Tunnel (`cloudflared` deployed from `misarescu/frankie-cd`, its token from Scaleway Secret Manager) or an Ingress; the control plane stays inside the cluster.
- Settings gains Users; the sidebar's footer shows who is signed in.
- **Done when:** Frankie's UI on Kapsule is reachable at its public hostname, only after signing in, with a password and with at least one single sign-on provider; every API path answers 401 without a session or token; a viewer cannot decide a gate; a decided gate records the person who decided it.

## M11 - Git connections

Frankie knows one provider (GitHub) and one credential, and its repositories are Helm values. M11 lets an administrator connect git hosts and add repositories from the UI, starting with GitLab and Bitbucket next to GitHub. Several repositories in one project come later, but the schema allows them from the start.

- **Connections:** a provider (GitHub, GitLab, Bitbucket), its URL (the cloud service or a self-hosted instance) and a credential, added in Settings by an administrator: a GitHub App installation (short-lived tokens per repository; a fine-grained token as fallback), a GitLab group or project access token, a Bitbucket access token. Where credentials are kept is open question 23.
- **Repositories** move from the Helm values (`repos`) into Postgres, added from a connection's list with their key prefix (D22) and base branch; an existing deployment's Helm list seeds them once.
- **Projects:** a project links to its repositories (`project_repositories`), one each for now.
- **Providers:** everything GitHub provides today behind `IssueSource`, `IssueWriter` and `ChangeRequestSource`, the merge queue's CI status (D90), releases (D129) and the drivers' `Repo` gets a GitLab and then a Bitbucket implementation, chosen by the repository's connection. What a provider lacks (Bitbucket has no sub-issues; GitLab epics live on groups) is checked at save time against what the project uses.
- The git proxy takes the upstream credential from the repository's connection; agents' tokens stay scoped to `agent/<issue-key>/*` (D21). The control plane and the git proxy reach a self-hosted instance through the egress allowlist.
- Not in M11: git hosts with no API (open question 24), several repositories in one project.
- **Done when:** a GitLab repository, added from the UI with no Helm change, runs an issue from sync through the merge queue next to the GitHub projects; a GitHub repository added through the GitHub App does the same; a Bitbucket repository syncs its issues and merges a change request.
