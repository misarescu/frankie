# 11 - Open questions and spec inconsistencies

## Open questions

1. **Kata memory overhead.** The concrete profile sizing does not include per-pod VM overhead or page cache. First measurement (2026-11-13, kata-deploy 4.3.1, `qemu-runtime-rs`, idle busybox pod): ~280 MiB host RSS per pod (QEMU 243, shim 27, virtiofsd 12). The `kata` RuntimeClass declares `overhead.podFixed` of 320Mi / 250m, so the scheduler accounts for it: 3 concurrent pods cost ~1 GiB, cutting the laptop headroom from 2.3 to ~1.3 GiB. Still open: overhead under real build load and page cache; revise `09-deployment-profiles.md` once measured in M1.
2. ~~**Nested virtualization.** Required if Kubernetes nodes are VMs. Confirm the target host is bare metal (the laptop) or that nesting is enabled.~~ Resolved: the laptop host is bare metal (i5-7300HQ, VT-x enabled, `/dev/kvm` present, Ubuntu 26.04); Kata runs there (`deploy/kata/`).
3. **In-cluster registry (full profile).** Harbor (heavier; scanning, proxy cache) vs Zot (lightweight). The concrete profile uses `registry:2`.
4. **Dependency proxy (full profile).** One Nexus, or one proxy per ecosystem (Athens, Verdaccio, devpi).
5. **Preview limits.** How many concurrent previews the homelab can hold, and their TTL.
6. **ACP adapter maturity.** Whether to rely on ACP for Claude Code/pi or on their native protocols. M4 starts with native protocols (D49: opencode's HTTP server, which already offers native mid-turn steering); revisit ACP once all three adapters exist, if it would replace three adapters with one.
7. **Auth.** Single-user token vs OIDC. Needed before exposing the UI beyond Tailscale. Since M3 the UI can approve human gates, including protected-path changes, so anyone who reaches the API can decide them and name themselves as the decider (D43); until this is resolved the API must stay reachable only through port-forward or Tailscale.
8. **Secrets management.** SOPS vs external-secrets for the GitOps repo.
9. ~~**Migration tool.** golang-migrate vs goose. Decide in M0.~~ Resolved by D19 (Atlas authors, goose applies).
10. **Spec approval placement.** This spec puts spec approval in the issue lifecycle (`refining` > `ready`) before a workflow starts, rather than as a workflow step. Confirm, or move it into the default workflow as a `human` gate.
11. **Merge approval default.** Decision D10 is auto-merge once gates pass. An earlier note listed PR merge as a human gate "initially". Confirm that auto-merge is the default and whether a per-project `human` gate before `enqueue` should be recommended for the first weeks. Input from the first self-hosted run (frk-1, M3): when a person approves a human gate that sits after the change request (the forced `protected-changes` gate, D44), they expect the approval to merge the change request; what a rejection should do to the change request (close it, leave it open, comment) is undecided. Decide with the merge queue (M6).
12. **Object storage for transcripts.** MinIO, S3-compatible service, or PVC directory (concrete profile).
13. ~~**Branch naming and issue ID format** (`agent/<issue-id>/<slug>`) - finalize with the GitHub token scoping rule.~~ Resolved by D22 (issue keys like `frk-42`, branches `agent/frk-42/<slug>`) and D21 (branch scoping enforced by the git proxy).
14. ~~**AppArmor blocks Postgres on the homelab host.**~~ Resolved by D28: the cause is Ubuntu 26.04's `kernel.apparmor_restrict_unprivileged_unconfined=1`, which stacks containerd's profile so it denies all signals inside containers (not only Postgres; also Prisma in LiteLLM and Go's SIGURG). Fixed on the host (`deploy/host/`); the per-pod Unconfined workaround is gone.
15. ~~**Toolchain registry write isolation.** The concrete profile's `registry:2` has no authentication, so a build pod (whose `mise.toml` may come from an unreviewed agent commit) could push to any tag, including another repo's toolchain image.~~ Resolved by D45: the registry is no longer trusted. Builds push by digest only and report the digest through the kubelet; the control plane verifies the manifest exists, records the digest per repository and tag in Postgres, and pods run toolchain images by that digest. A build pod can still write to the registry, but nothing reads what it writes unless the control plane recorded it from a build of those exact inputs.
16. **Dependency images, open points for M3.1.** ~~(a) How the declared files keep their directory paths in the build context.~~ Resolved by D47: the context is a tar archive in the ConfigMap's `binaryData`. ~~(b) BuildKit pulling `FROM` the plain-HTTP in-cluster registry.~~ Resolved by D47: a `buildkitd.toml` in the ConfigMap marks the registry `http = true`. (c) Still open: whether caches should also persist across runs beyond the image (a per-repo cache volume, or sharing caches between one gate's commands): only if M3.1's target is not met, since any cache a pod can write and another pod reads conflicts with invariant 2. (d) Build speed: a build Job unpacks its base image for about 10 minutes, and a `COPY` of a few small files took 6 minutes, which suggests BuildKit uses its copying "native" snapshotter because its scratch volume (an emptyDir over Kata's shared filesystem) cannot host overlay mounts. Frankie's dependency image took 29m44s and over 10 GiB of scratch (D47; limits raised to 50 minutes and 30 GiB). Candidates: an overlay-capable scratch filesystem inside the VM (a loop-mounted ext4 image, or a block volume). Verify the snapshotter first.
